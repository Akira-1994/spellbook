# Spellbook 本機校對介面設計

日期：2026-09-18

## 1. 目標

建立一套供非技術校稿者使用的單人本機校對工具，涵蓋目前 A–Z 全部 2,360 筆法術，而不只限於生成翻譯或異常條目。

應用程式以瀏覽器呈現三欄工作台，但只連接本機服務。校稿者使用免安裝的 Windows 可攜式程式，不需要安裝 Python、Node.js 或其他開發環境。

不同協作者可以各自在本機校對，再透過 Git 合併不可變校對事件。每次正式修改都必須保留編輯者名稱、修改前後內容、時間、備註及核對結果。

## 2. 成功條件

- 全部 2,360 筆法術均可搜尋、編輯、核對與標記完成。
- 支援一般條目、生成翻譯、同名條目及後續新增的問題類型。
- 中英文名稱、規則欄位、正文及 PDF 來源四類核對全部完成後，才能將條目標記為 `reviewed`。
- 正式修改同時更新本機 SQLite 並產生不可變、可由 Git 合併的事件檔。
- 不同協作者修改不同欄位時可以自動合併；同欄位出現不同修改時必須建立衝突任務。
- 同名法術的合併不刪除舊 ID、原始條目或修改歷史。
- 應用程式可以建立範圍受限的 Git commit，但不得自動 push。
- Windows 10／11 x64 校稿者可直接執行可攜式程式。
- 斷網時除 Git pull／push 外，所有校對功能皆可運作。

## 3. 使用者與執行環境

第一版為單人本機應用程式，不提供帳號、權限或多人即時協作。

每個本機實例只有一位目前編輯者。編輯者名稱預設讀取 `git config user.name`，首次啟動時必須確認，也可在本機設定中覆寫。設定保存在 `%LOCALAPPDATA%\SpellbookReviewer\settings.json`，不提交至 Git。

校對事件保存已確認的 `editor_name`。建立 Git commit 時，應用程式顯示 Git 的作者姓名及電子郵件；若 Git 作者姓名與校對者名稱不一致，必須先確認或修正，應用程式不得默默修改全域 Git 設定。

## 4. 技術方案

### 4.1 應用程式

- Python FastAPI 提供本機 HTTP API 與伺服器端頁面。
- Jinja 產生 HTML，搭配少量原生 JavaScript 處理編輯、鍵盤操作與局部更新。
- 所有前端資源隨應用程式封裝，不使用 CDN。
- 使用 PyInstaller 或等效工具產生 Windows x64 可執行檔。
- 啟動器只監聽 `127.0.0.1` 的隨機可用連接埠，啟動後自動開啟預設瀏覽器。

### 4.2 安全邊界

- HTTP `Host` 僅接受 localhost／127.0.0.1 與實際啟動連接埠。
- 每次啟動產生隨機工作階段密鑰。
- 所有修改 API 需要同源檢查及 CSRF token。
- PDF 僅能從設定的專案根目錄讀取，API 不接受任意檔案路徑。
- Git 元件只能操作目前專案，不接受任意 shell 指令或未驗證路徑。
- 程式不得在校對期間向外部網路傳送法術內容。

## 5. 資料權責

### 5.1 Git 合併依據

導入校對事件後，版本控制中的可合併權威資料為：

```text
不可變基準資料 + 不可變校對事件
```

SQLite 仍是本機應用程式執行時的 CRUD、搜尋與關聯查詢主體，但也是可由基準資料及事件重建的投影。JSON 匯出與報告同樣是衍生產物，不接受直接編輯。

這項調整取代原本「SQLite 是唯一可信來源」的描述，原因是 SQLite 二進位檔無法可靠地透過 Git 三方合併。

### 5.2 版本控制檔案

```text
data/baseline/spells-v1.json
reviews/changes/<event-ulid>.json
data/spellbook.sqlite
data/export/spells.json
reports/*
```

`data/baseline/spells-v1.json` 由導入校對系統前的已驗證資料產生。建立後不可直接修改；基準格式若需升級，必須建立新版基準及 migration，不得覆寫舊版。

### 5.3 本機檔案

草稿、單一實例鎖、暫存檔及自動備份不提交 Git。草稿使用獨立的本機 sidecar SQLite，而不是 `data/spellbook.sqlite`，避免未完成內容進入共享資料：

```text
%LOCALAPPDATA%\SpellbookReviewer\projects\<project-hash>\reviewer.local.sqlite
```

## 6. 校對事件

每次「儲存修改」「通過校對」「解決衝突」「設定版本關係」或「確認合併」都建立一個事件檔。檔名使用事件 ULID，避免不同協作者產生 Git 路徑衝突。

事件至少包含：

```text
event_id
schema_version
editor_name
occurred_at_utc
spell_id
spell_entry_id
action
base_revision_hash
changes[]
completed_checks[]
note
```

每個 `changes[]` 元素包含欄位路徑、修改前值與修改後值。事件使用固定 JSON 格式、UTF-8 及穩定鍵順序，方便 diff、測試與重建。

事件檔建立後不可修改或刪除。需要撤銷時建立反向事件，不重寫歷史。

## 7. SQLite 擴充

主資料庫增加下列投影或欄位：

- `review_events`：已套用事件的 ID、雜湊與套用時間。
- `review_checks`：法術、內容版本、核對類型、編輯者與完成時間。
- `review_conflicts`：欄位路徑、競爭事件、候選值及解決狀態。
- `spells.merged_into_id`：合併後指向保留的主要 ID。
- `spells.record_status`：`active` 或 `merged`。
- `spells.reviewed_revision_hash`：通過時的內容版本。

原有 `variant_group_id` 用於關聯英文同名但規則不同的法術版本。

只要已通過條目的內容版本改變，`reviewed_revision_hash` 即失效，條目自動回到 `needs_review`；舊核對紀錄仍保留。

## 8. 使用者介面

### 8.1 三欄工作台

左欄：

- 中英文名稱、ID 與正文搜尋。
- 全部、尚未校對、需要校對、已校對等進度佇列。
- 生成翻譯、英文同名、衝突及已修改未通過等問題佇列。
- A–Z、來源、學派、職業與等級篩選。
- 目前條目清單及鍵盤導覽。

中欄：

- 中英文標準名稱。
- 學派、子學派、描述符、等級、成分、施法時間、距離、目標、區域、效果、持續時間、豁免、法術抗力與代價。
- 中文正文、英文正文及未加工原文。
- 儲存草稿、儲存修改、通過並前往下一筆。
- 未儲存變更、目前 revision 及最後編輯者提示。

右欄：

- PDF 實際頁面及上一頁／下一頁導覽。
- 來源書籍、解析信心與問題標記。
- 修改歷程、核對紀錄及衝突資訊。

### 8.2 全資料範圍

介面不得以 `needs_review` 作為可編輯範圍。全部 2,360 筆均可開啟、修改與核對；翻譯及同名條目只是預設問題佇列。

### 8.3 核對條件

每筆法術包含四個必要核對類型：

1. 中英文名稱。
2. 規則欄位與數值。
3. 中文／英文正文。
4. PDF 頁碼與原始內容。

四類核對必須對應同一個內容 revision。全部完成後才啟用「通過並前往下一筆」。不為每個小欄位建立獨立狀態。

## 9. 工作流程

### 9.1 一般條目

1. 從搜尋或佇列選取條目。
2. 比對欄位、原文、PDF 及歷程。
3. 需要時修改內容。
4. 完成四類核對。
5. 儲存並通過條目。

即使內容不需要修改，也必須建立通過事件，保留校對者及 revision。

### 9.2 生成翻譯

介面額外並排顯示英文正文與中文譯文。通過時：

- `review_status = reviewed`
- `translation_status = reviewed`

原始英文正文及翻譯來源不可因校對而刪除。

### 9.3 同名條目

同組條目並排顯示欄位與正文差異。可選擇：

- 同一法術，應合併。
- 不同規則版本。
- 名稱解析錯誤。
- 暫不確定。

合併必須先顯示保留值、來源、ID 與關聯變更預覽。確認後保留主要 ID；其他 ID 設為 `record_status = merged` 並填入 `merged_into_id`。舊 ID、原始條目、來源及事件不得刪除。

### 9.4 草稿

輸入內容自動保存於本機 sidecar SQLite，以防瀏覽器關閉或程式中斷。草稿不改變正式資料、不產生校對事件，也不進入 Git。

使用者按下「儲存修改」後，系統才驗證並建立正式事件。離開仍有未儲存修改的條目時，介面必須警告。

## 10. 原子寫入與恢復

正式儲存依序執行：

1. 驗證輸入、基準 revision 及事件格式。
2. 將事件寫入同檔案系統的暫存檔並 flush。
3. 開始 SQLite transaction。
4. 套用資料修改並加入 `review_events` 索引。
5. 將事件暫存檔原子重新命名為正式事件檔。
6. 提交 SQLite transaction。

若事件建立失敗，SQLite transaction 回滾。若事件已重新命名但 SQLite commit 失敗，下次啟動時以事件為依據重新套用；事件重播必須具備冪等性。

應用程式以專案鎖避免兩個本機實例同時寫入。執行 migration、重建或同名合併前，先建立本機 SQLite 備份。

## 11. 衝突處理

事件以 `base_revision_hash` 及各欄位修改前值執行三方判斷：

- 修改不同欄位：自動合併。
- 同欄位修改成相同值：視為一致。
- 同欄位修改成不同值：建立 `review_conflicts`，不自動選擇勝方。

衝突介面並排顯示基準值、事件 A、事件 B、編輯者、時間與備註。解決衝突會建立新事件，原競爭事件保留。

若 Git 合併造成 SQLite、JSON 或報告衝突，應用程式提供「重建衍生檔」功能：

1. 確認基準資料及所有事件檔已合併。
2. 從乾淨資料庫套用 migration。
3. 依事件規則重播全部事件。
4. 產生欄位衝突任務。
5. 重建 FTS5、JSON 與報告。
6. 執行驗證後，將衍生檔標記為 Git 衝突已解決。

校稿者不需要手動合併 SQLite 二進位內容。

## 12. Git Commit

介面提供「建立校對 Commit」，但不提供 push。

建立前必須：

- 顯示本批條目、事件、編輯者與檔案清單。
- 重建 JSON 與報告。
- 通過資料庫、事件、JSON Schema、外鍵、FTS 及重建一致性驗證。
- 確認 Git 不處於未解決的 merge／rebase 狀態。
- 確認暫存區沒有介面建立前就存在的其他檔案。

Git 元件只能以明確路徑加入允許清單內的校對事件、SQLite、JSON 與報告。其他未提交修改可以留在工作區，但不得被介面加入暫存區或 commit。

預設 commit 訊息格式為：

```text
Review <count> spell entries
```

介面建立 commit 後顯示 commit hash，並提示使用 GitHub Desktop 或命令列檢查及 push。

## 13. 啟動檢查與錯誤模式

啟動時檢查：

- 編輯者名稱已確認。
- 專案、PDF、基準資料、SQLite 及事件目錄存在。
- schema version 與應用程式相容。
- SQLite integrity、foreign key 與 FTS 筆數正確。
- 事件檔格式正確且套用狀態一致。
- Git repository、目前分支與 merge 狀態可辨識。

失敗時進入唯讀診斷頁，顯示可理解的問題、可能影響與建議操作。不得在檢查失敗時自行覆寫資料。

## 14. 測試策略

### 單元測試

- 事件 Schema、穩定序列化與雜湊。
- 欄位 patch、事件重播及冪等性。
- 核對 revision 與狀態失效。
- 欄位層級三方衝突判斷。
- 同名合併及反向事件。

### 整合測試

- SQLite transaction、migration、外鍵與穩定 ID。
- 事件檔與資料庫的原子寫入及故障恢復。
- API 搜尋、草稿、修改、核對、通過及衝突解決。
- Git 允許清單、既有暫存檔防護及 commit 建立。
- 基準資料加事件可重建完全一致的 SQLite／JSON／報告。

### 端對端測試

- 一般條目完成校對。
- 生成翻譯修改並通過。
- 同名條目判定版本及安全合併。
- 兩位協作者的非衝突與衝突事件。
- Git 衍生檔衝突重建。

### 發行測試

- Windows 10／11 x64 解壓縮可攜式 ZIP。
- 雙擊 EXE 啟動服務與瀏覽器。
- 斷網完成一筆測試校對。
- 關閉應用程式後本機服務停止。

## 15. 發行方式

- 第一版支援 Windows 10／11 x64。
- 發行未簽章、免安裝的可攜式 ZIP。
- 每個發行產物附 SHA-256 校驗碼。
- README 說明 SmartScreen 警告、校驗方式、GitHub Desktop 工作流程及資料備份。
- GitHub Actions 在 Windows runner 建置並執行 smoke test。
- 建置流程預留未來加入程式碼簽章的位置。

## 16. 非目標

第一版不包含：

- 帳號、權限與多人即時協作。
- 自動 Git push 或遠端 repository 管理。
- macOS／Linux 正式發行產物。
- PDF 編輯、OCR 或重新排版。
- 雲端同步或外部翻譯服務。
- 行動裝置介面。

## 17. 交付內容

- FastAPI 本機校對服務。
- 三欄瀏覽器工作台。
- 基準資料、事件 Schema、重建與衝突工具。
- Git commit 工具及衍生檔衝突重建流程。
- 單元、整合、端對端與 Windows smoke tests。
- Windows x64 可攜式 ZIP 與 SHA-256。
- 使用者操作、GitHub Desktop 協作及故障排除文件。
